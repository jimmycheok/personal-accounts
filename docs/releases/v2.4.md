# Release v2.4 — GL-Sourced Cash Flow, Dashboard & Borang B Tax

**Date:** 2026-08-10
**Branch:** feat/gl-sourced-cashflow
**Base commit:** f46878e

## Summary

Fixes a reported production bug: a **Payment Voucher was created, its account code was recorded, but the expense never appeared in cash flow**.

Root cause — Cash Flow, the Dashboard and the Borang B tax calculator all read the `expenses` and `invoices` tables directly, while Payment Vouchers only ever write to `journal_entries`. Payment Vouchers were therefore invisible to all three surfaces, while appearing correctly in the GL-sourced Reports.

This release inverts that dependency: the **General Ledger becomes the single source of truth** for money figures, so every module that posts a journal entry is counted identically. Because that is only safe if the GL is complete, GL posting was first made unconditional across every financial write path, and a backfill tool added for historical gaps.

| Surface | Before | After |
|---|---|---|
| Cash Flow | `expenses` table only | GL — debit to `1000`/`1010` = inflow, credit = outflow |
| Dashboard totals | `expenses` / `invoices` | GL (same query as cash flow, so they now agree) |
| Borang B tax | `expenses` table | GL, grouped by `accounts.borang_b_section` |
| Reports (P&L, Balance Sheet) | already GL | unchanged |

Measured on real data: the RM1,800 payment voucher now appears as cash outflow (previously RM599, the expenses table alone), reaches **D2** in Borang B (previously RM0), and the dashboard and cash flow report identical figures.

## Bug Fixes

| Area | Fix |
|---|---|
| Payments | **Every cash payment posted to Bank instead of Cash.** `payments.js` wrote `payment_method` while the model attribute is `method`, so Sequelize silently dropped it and the value always fell back to the default |
| Tax | **A year-end close would have zeroed the entire Borang B computation.** `getExpensesBySection` lacked the `year_end_close` filter that `ReportService` has, so after a close every expense account nets to zero |
| Tax | **Mileage was double-counted in D5** — the GL posts it to `6400` (D5) and `TaxCalculator` added it again, at a different rate |
| Tax | Voiding a sent invoice drove Borang B income to `−total` (the entry was deleted *and* a reversal posted). Voids now reverse only. Same fix, inverted, for credit notes |
| Cash flow / Dashboard | Two timezone date-boundary bugs — `.toISOString()` on locally-constructed dates shifted windows a day on UTC+8. One was live on dashboard deadlines before 08:00 MYT |
| GL | `markPaid` stored `NULL source_id`, making those entries unreconcilable by any void/reversal lookup |
| GL | Voiding a paid invoice left the payment-side entry behind — a permanent phantom cash inflow |
| GL | Expense and invoice edits never reached the GL, leaving stale entries |
| Web | Side nav never collapsed, pushing primary action buttons off-screen below ~850px on **every** page |

## Spec Changes

- **New account `6995` Non-Deductible Expenses** with `borang_b_section = NULL`. This replaces `Expense.is_tax_deductible` as the exclusion mechanism: the tax query filters `WHERE a.borang_b_section IS NOT NULL`, so non-deductible spend is excluded from Borang B *structurally* while still appearing in Profit & Loss.
- **Cash is defined as accounts `1000` and `1010` only.** Credit Card (`2300`) is a liability — a card purchase becomes a cash outflow only when the card is paid. Inflow = debit to a cash account; outflow = credit.
- **GL posting is now unconditional** at every financial write path (expense create, payment, invoice send, invoice mark-paid, mileage, recurring-entries job). Where the client sends no reviewed `journal_lines`, the server derives them. Each site uses a compensating rollback: if the GL post fails, the source record is removed and the original error rethrown.
- **Borang B income is now accrual**, taken from revenue accounts, rather than cash-received from `invoices.paid_at`. ⚠️ **This changes what is reported on a tax return — confirm with a tax agent before filing.**
- **D15 Entertainment deductibility** is now read from `BORANG_B_SECTIONS[...].deductibilityRate` in the shared constants rather than a hardcoded `0.5`, so the rate lives in exactly one place.
- Only `journal_entries.status = 'posted'` entries count, and `source_type IS DISTINCT FROM 'year_end_close'` is applied to every ledger query (`IS DISTINCT FROM`, not `!=`, so NULL `source_type` rows are not silently dropped).
- **Test tooling introduced**: `node:test` for API unit tests (26) and Playwright for browser E2E (12). The repository previously had no test framework.

## Upgrade Notes

Rollout order matters — the full procedure is in `docs/superpowers/plans/2026-08-06-gl-sourced-cashflow.md`.

1. **Seed the new account first** — it is a hard prerequisite. Without `6995`, every non-deductible expense throws:
   `cd apps/api && npx sequelize-cli db:seed --seed 20260806000001-non-deductible-account.cjs`
2. **Back up the database.** The backfill writes to live accounting data and has no undo.
3. **Deploy the API before running the backfill.** Running the backfill first lets the old API open fresh gaps behind it (the daily 06:00 recurring-entries job makes this concrete).
4. **Dry run the backfill and read the counts:** `node scripts/backfill-journal-entries.js`
5. **Hard gate:** do not run `--apply` unless both the AMBIGUOUS count and the orphan (`source_id IS NULL`) count are zero. Resolve them by hand first — an ambiguous match can mean the money is already in the ledger under a different entry.
6. **Apply** (one operator, one run — the script has no inter-process lock): `node scripts/backfill-journal-entries.js --apply`
7. **Verify** dashboard totals, cash flow totals **and** Borang B agree.

No new environment variables. No new npm dependencies for the API (`node:test` is built in); Playwright is a `devDependency` of `apps/web`.

## Known Follow-Ups (not in this release)

- `/export/full-backup` omits `accounts`, `journal_entries`, `journal_entry_lines` and `payment_vouchers` — restoring from it would lose every money figure on the converted surfaces.
- `is_capital_allowance` on `ExpenseCategory` is dead code, so capital items (computers, equipment) are deducted in full in year one instead of via capital allowances.
- `TaxCalculator.getMileageDeduction` uses a flat RM0.25/km against the documented tiered RM0.60 / RM0.40 rate.
- `source_type='payment'` holds two id namespaces — `markPaid` writes invoice ids alongside real payment ids. The backfill reports ambiguity rather than guessing.
- Void handlers lack a terminal-status guard; a repeated void via direct API compounds the reversal (not reachable from the UI).
- `ReportService` still uses `!= 'year_end_close'` rather than `IS DISTINCT FROM`.
