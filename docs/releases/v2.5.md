# Release v2.5 — Mileage Tax Correctness & Payment Voucher PDF Fix

**Date:** 2026-08-11
**Branch:** release/v2.5
**Base commit:** ea03da2

## Summary

Two fixes, both found by looking at what the code actually did rather than what the docs claimed.

The **payment voucher PDF** was unusable — clicking it opened a tab showing `{"error":"No token provided"}`. It now downloads correctly.

The **mileage feature carried a tax-correctness problem**. The codebase described its per-km figure as an "LHDN-approved tiered rate", which does not exist: LHDN publishes no per-km rate for a sole proprietor's business deduction, and the RM0.60/first-200km figure is the Malaysian civil service rate, which does not govern private businesses. Worse, mileage claims and actual vehicle receipts both posted to account `6400`, so claiming the same trip under both bases was invisible. Mileage now posts to a dedicated `6410 Mileage Claim` account — still Borang B **D5**, so no tax figure changes — and the app flags months where both bases were used.

## Spec Changes

- **New account `6410` Mileage Claim**, `borang_b_section: 'D5'`. Both `6400` and `6410` carry D5, so **the Borang B D5 total is unchanged** — the split exists purely so the two claim bases are distinguishable in the ledger and in reports.
- **`GET /taxation/borang-b` response gains `mileageOverlapMonths`** — an array of months where both accounts posted activity, with each side's total. Informational; it does not affect any computed figure.
- **`LedgerQueryService.getMileageOverlapByMonth(from, to)`** added.
- **Mileage rate is documented as the owner's own estimate**, default RM 0.60/km via `MILEAGE_RATE_PER_KM`, overridable per trip. LHDN prescribes no per-km rate for a sole proprietor; the statutory basis is actual costs apportioned by business use under s.33(1) ITA 1967, substantiated by a logbook. The calculation itself (`km × rate`) is unchanged.
- **README corrections** where the previous text did not match the code: cash flow projection does not use "historical averages"; only e-invoice types `01` and `02` are implemented (`03`/`11` are enum values only); `full-backup` omits the ledger tables; the v2.1 summary overstated what that release fixed.

## Upgrade Notes

**The `6410` seeder is a deployment prerequisite.** Apply it *before* the new code serves traffic, or logging a mileage trip fails — `onMileageLogged` cannot resolve the account.

```bash
cd apps/api
npx sequelize-cli db:seed --seed 20260806000002-mileage-claim-account.cjs
```

Under Docker, insert this between the migration step and `up -d`:

```bash
COMPOSE="docker compose -f docker-compose.prod.yml"
$COMPOSE run --rm api npx sequelize-cli db:seed --seed 20260806000002-mileage-claim-account.cjs
```

> **Never run `db:seed:all` against a populated database.** `seederStorage` is not configured, so sequelize-cli re-runs every seeder — including `20260327000002-retroactive-journal-entries.cjs`, which has no existence guard and would duplicate every journal entry, doubling every figure on cash flow, the dashboard and Borang B. The account seeders (`6995`, `6410`) are individually guarded and safe to re-run.

No new environment variables. No migrations. Existing mileage entries keep their `6400` journal entries — only new logs post to `6410`. Re-point historical entries by hand only if you want the split applied retrospectively; the D5 total is identical either way.
